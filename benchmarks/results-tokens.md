# Token benchmark: what a search result costs a model to read

How many tokens `llm-semantic search` prints in each output mode, counted over the same ten searches of this repository. Every number below is re-counted from the outputs checked in under `outputs/`, offline, by one command:

```bash
make bench-tokens      # or: go run ./benchmarks/cmd/count-tokens
```

It prints the tables below and exits 1 if this file disagrees with them. `go test ./benchmarks/` makes the same check, so CI fails when an output or a number here is edited without the other.

### Why plain text is the smallest

The three modes do not carry the same information, and the counts show what each one costs:

- **`--json`** carries every field of every result: the whole chunk content, untruncated, its id, line range, language, signature and a preview. Its schema is kept as it was before the AXI work (board decision, 2026-10-31; see [docs/axi-conformance.md](../docs/axi-conformance.md)).
- **`--axi`** carries four fields per result (`file` as `path:line`, `name`, `score`, `content`), with `content` cut at 200 characters of the chunk body plus a note of how much was left out. Around the results it adds the query, the `total`, a `help` list of next steps and the `stale` object. Those are what a model needs to act on the answer without a second call.
- **Plain** prints a numbered list: path and line, name, type, relevance label, score, and a one-line preview of at most 150 characters, which for a function is its signature rather than its body. With a fresh index it prints no staleness line. It is the smallest because it shows the least of each result, not because the encoding is denser.

So plain is a list of where to look, and `--axi` is the start of what is there. The number to quote for `--axi` is its ratio to `--json`, with that caveat.

## Method

- **Corpus and tool, pinned.** The index is built from this repository at commit `573311bad7007b55c009ec0d8746244a94038fc4` (`PinnedCommit` in `generate.go`), and the CLI that renders the results is built from the same commit. The benchmark files themselves were added after it.
- **Queries.** The ten questions in `queries.txt`, fixed. Each is run once per mode as `llm-semantic search "<query>"` with `--json`, `--axi`, or no flag, and default settings otherwise (`--top 10`, dense search, the `code` profile, sqlite storage).
- **Same results in every mode.** All three modes of a query read the same index with the same query vector, so they render the same ten results; only the rendering differs. The generator refuses to write outputs for a query whose `--json` result list is empty, so no number here measures an empty answer, and it refuses a `--axi` or plain output whose stated count (`total: N`, `N results for`) differs from the `--json` count.
- **What is counted.** Standard output only, as the command prints it. In `--json` mode the staleness line goes to standard error and is not counted; in the other modes there is none, because the index is fresh.
- **Paths.** The commit is checked out into a temporary directory; the generator rewrites that directory to `/work/llm-semantic-axi` in every output so the files do not depend on the machine they were made on, and refuses to write an output in which the temporary path survives.
- **Embeddings.** No embedding model was used. The outputs were generated against `HashEmbedder` (`generate.go`), a stand-in endpoint on the loopback interface that splits text into words (identifiers at camelCase and `_`), drops stopwords and hashes each word into one of 4096 buckets. It is a keyword match, not a semantic model, so **which** results come back is not what a real model would return. That does not affect the comparison, which is between three renderings of the same results; it does mean the absolute counts depend on this result mix (more prose chunks, for example, would raise `--json` and `--axi` more than plain).

## Tokenizer

- **Encoding:** `cl100k_base`, through the pure-Go [`github.com/pkoukk/tiktoken-go`](https://github.com/pkoukk/tiktoken-go) v0.1.8 (Go module dependency) with its split pattern and special tokens.
- **Ranks file:** `cl100k_base.tiktoken`, vendored unchanged from OpenAI (`https://openaipublic.blob.core.windows.net/encodings/cl100k_base.tiktoken`). The counter checks its sha256 against `223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7` (the hash tiktoken itself checks) and refuses any other file. It never downloads anything.
- **Compatibility check:** `TestCL100KMatchesKnownTokenIDs` asserts the token IDs tiktoken gives for two reference strings.
- Special-token text such as `<|endoftext|>` is counted as ordinary text.

**This is an approximation.** `cl100k_base` is the tokenizer of OpenAI's GPT-4 and GPT-3.5 models. Claude and other models use their own tokenizers, so the token count a given model sees will differ. Treat the absolute numbers as an estimate and the ratios between modes as the more portable figure; they too will shift somewhat between tokenizers.

## Re-counting

```bash
make bench-tokens            # re-count, print, fail on a mismatch with this file
make bench-tokens-write      # re-count and rewrite the tables above
```

Re-counting needs the Go toolchain and the module cache (`go mod download` once); after that it uses no network and no embedding endpoint. It reads `queries.txt`, `outputs/` and the vendored ranks file, and refuses a missing, extra or empty output rather than count around it.

## Regenerating the outputs

```bash
make bench-generate          # or: go run ./benchmarks/cmd/generate [-commit <sha>]
make bench-tokens-write
```

`generate` checks the pinned commit out into a temporary `git worktree`, builds `llm-semantic` from it, starts `HashEmbedder` on `127.0.0.1`, runs `llm-semantic index .`, runs every query in every mode and writes `outputs/`, then removes the worktree. It needs `git` and `go` and makes no network call.

A regeneration is not a byte-for-byte copy. Scores move slightly between runs (in the third decimal place; the cause is not yet traced and is filed as technical debt), so results with close scores can swap places and the relevance labels (`low`/`medium`) can change. A review regeneration returned the same ten results for every query, but in a different order for three of them. Chunk ids (`--json`) are hashed from the absolute path of the temporary checkout, and `indexed_at` (`--axi`) is the time of the run. Expect the counts to move by a few tokens. The checked-in outputs are the record; the numbers above are theirs.
